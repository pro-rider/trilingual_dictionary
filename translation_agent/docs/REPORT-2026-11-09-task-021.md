## A. Model parameters are now identity — VERIFIED

Finding was correct: `pipeline` passed `model_parameters=None` while v2 supported
the field.

Change: `Provider.parameters()` is part of the protocol (`FakeProvider` returns
`{"temperature":0.0,"deterministic":true,"max_tokens":64}`; a provider with no
settings returns `{}`, `None` is refused). The pipeline reads it once, hashes it
into request fingerprint v2, and stores it as canonical JSON in the new
`generation_requests.model_parameters` column.

Evidence: `tests/test_fingerprint_v2.py::test_changing_a_generation_parameter_changes_the_request`
— same sense, temperature 0.0 vs 0.7 → 2 requests, 2 distinct fingerprints, and
the stored parameters differ. CLI run shows
`{"deterministic":true,"max_tokens":64,"temperature":0.0}` in the row.

Schema impact: `model_parameters` is a new column → schema version `2 → 3`,
contract `TA-CONTRACT-0.3`. A v2 ledger is refused, not migrated.

## B. Expression-index blind spot — VERIFIED (closed)

Finding was correct and subtle: `PRAGMA index_info()` reports `NULL` as the
column name of an expression index, so `COALESCE(variant_key,'base')` was
invisible to the old comparison; only uniqueness/columns/partiality were
compared.

Change: `introspect()` now also hashes each index's normalised DDL from
`sqlite_master`, which carries the expression, `COLLATE`, `ASC`/`DESC` and the
`WHERE` predicate. Index DDL hashes are compared and folded into
`schema_fingerprint`.

Evidence: `tests/test_schema_verifier.py` — a rewritten expression
(`COALESCE(variant_key, variant_key || 'x')`), a `COLLATE NOCASE` index, a
`DESC` index and a partial index with `WHERE state='approved'` are each rejected.
Verified that a case-only change (`'BASE'` vs `'base'`) does **not** trigger:
normalisation lowercases, so it is the same index, and the test says so.

## C. Manifest identity independent of existence — VERIFIED

Finding was correct: the manifest path check lived inside `if resolved.exists()`,
so a reserved path could be created fresh by SQLite.

Change: manifest-listed paths are compared after `realpath` **before** the
existence branch; inode/content checks still require a file. Manifest entries are
now type-validated (`path` non-empty string, `dev`/`ino`/`bytes` integers,
`sha256` 64 hex chars, `captured_at` string) and any violation fails closed.

Evidence: `tests/security/test_guard_bypass.py::test_manifest_listed_path_is_refused_before_it_exists`
(nonexistent reserved path refused), plus bad-`sha256`, non-integer inode, and
missing-`path` tests.
End-to-end on a throwaway copy: manifest captured → `guard` reports
`entries 1, inode_identity true, content_identity true, hardlink_protection true`;
a hard link to that copy is refused with
`it is the same file (dev/ino) as protected …`; an unrelated path is allowed.

## D. Failed provider attempts — DECIDED, VERIFIED (contract decision, your veto applies)

Two options were open. I chose **atomicity over partial history** and wrote it
down instead of leaving it implied:

- a failed batch persists **nothing**, including `provider_attempts` and
  `raw_responses`;
- the failure is raised with the provider error class preserved
  (`ProviderTimeout` / `ProviderInvalidJSON` / `ProviderFailure`), the message
  names the failing sense and the attempt count, and carries no secret.

Evidence: `tests/test_atomicity.py::test_failed_batch_leaves_no_attempt_rows_and_reports_redacted_errors`
— a batch failing after two calls raises `ProviderFailure`, names
`fixture:1003`, contains no `sk-`/`api_key`/`bearer`, and all four tables
(`candidates`, `generation_requests`, `provider_attempts`, `raw_responses`) are
empty afterwards. Existing atomicity tests are unchanged and still pass.

If you would rather have a separate failure sink, that is a new component and I
will not silently add writes outside the batch transaction.
